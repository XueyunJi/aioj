# 测试用例大规模上传出现的问题以及解决方案

## 1. 文档目的

本文记录 AIOJ 在上传大规模测试用例 ZIP 包时出现的兼容性、容量限制、性能和错误提示问题，并给出与当前源码一致的修复方案。

本文讨论的“包大小”必须区分以下概念：

1. ZIP 压缩文件大小。
2. ZIP 解压后的全部文件总大小。
3. 单个测试点文件大小。
4. ZIP 内文件条目数量。

不能使用同一个含糊的“50 MB 限制”描述上述四项，否则管理员无法判断失败发生在哪个环节。

## 2. 已复现问题

### 2.1 复现对象

现有题目中存在一个已经上传并激活的测试包：

| 字段 | 值 |
| --- | --- |
| 文件名 | `88.zip` |
| 压缩文件大小 | `46,109,715` 字节，约 `43.97 MiB` |
| SHA-256 | `91d4280b1732596bc85f7dbbe11b827a03de90cfef1fec8822943600498dc982` |
| 测试点数量 | 88 |
| 状态 | `READY` |
| 是否激活 | 是 |
| 存储方式 | `LOCAL` |

该包可以从系统下载，但下载后重新选择同一 ZIP 上传时，页面显示操作失败，浏览器 Network 面板没有出现 `/init`、分片上传或 `/complete` 请求。

### 2.2 关键证据

该 ZIP 的压缩文件大小没有超过当前前端的 50 MiB 限制，88 个测试点也没有超过 2000 个 ZIP 条目的限制，已记录的单个 `.in` 或 `.out` 文件均没有超过 8 MiB。

但是，仅第 71 至第 88 组测试点的输入、输出文件合计就达到：

```text
103,808,121 字节，约 99.00 MiB
```

因此，不需要计算全部 88 组文件，就可以确定该 ZIP 解压后的总大小必然超过 50 MiB。

## 3. 当前源码中的限制

### 3.1 前端限制

文件：`apps/web-admin-react/src/components/TestcasePackagePanel.tsx`

当前前端使用硬编码常量：

```ts
const CHUNK_SIZE_BYTES = 4 * 1024 * 1024;
const MAX_CASE_FILE_BYTES = 8 * 1024 * 1024;
const MAX_PACKAGE_BYTES = 50 * 1024 * 1024;
const MAX_MANIFEST_BYTES = 1 * 1024 * 1024;
```

其中 `MAX_PACKAGE_BYTES` 同时被用于：

- 检查 ZIP 压缩文件大小；
- 检查 ZIP 解压后的文件总大小；
- 检查前端补入 `manifest.json` 后重新生成的 ZIP 大小。

用户选择文件后，`prepareSelectedFile()` 会在浏览器中调用 `analyzeZip()`。`analyzeZip()` 使用 JSZip 读取 ZIP 中每个条目的 `uncompressedSize`，累计值超过 50 MiB 后立即抛出异常。

这个过程发生在计算完整 SHA-256 和调用上传初始化接口之前。因此，在该阶段失败时，Network 面板看不到上传请求是符合当前代码逻辑的。

### 3.2 后端限制

文件：

- `backend/problem-service/src/main/resources/application.yml`
- `backend/problem-service/src/main/java/com/aioj/next/problem/config/TestcaseProperties.java`
- `backend/problem-service/src/main/java/com/aioj/next/problem/domain/testcase/TestcasePackageValidator.java`

当前默认配置如下：

| 限制项 | 默认值 | 环境变量 |
| --- | ---: | --- |
| ZIP 压缩文件 | 50 MiB | `AIOJ_TESTCASE_MAX_PACKAGE_BYTES` |
| 上传分片 | 4 MiB | `AIOJ_TESTCASE_CHUNK_SIZE_BYTES` |
| 单个用例文件 | 8 MiB | `AIOJ_TESTCASE_MAX_CASE_FILE_BYTES` |
| 解压后总大小 | 50 MiB | `AIOJ_TESTCASE_MAX_UNCOMPRESSED_BYTES` |
| ZIP 条目数 | 2000 | `AIOJ_TESTCASE_MAX_ENTRY_COUNT` |
| `manifest.json` | 1 MiB | 当前为后端常量 |

后端在 `/complete` 阶段合并分片后，使用 `TestcasePackageValidator` 逐条读取 ZIP 内容，并再次执行单文件大小、解压总大小、条目数、清单格式和路径安全校验。后端校验必须保留，它是不能被浏览器绕过的权威校验。

## 4. 根因分析

### 4.1 直接根因：解压总量超过前端固定上限

`88.zip` 压缩后约 43.97 MiB，但解压后的总量远超 50 MiB。前端在本地扫描阶段拒绝文件，因此没有上传网络请求。

### 4.2 历史数据兼容性缺陷

服务器数据库中的该包已经是 `READY` 且处于激活状态，说明它可能在以下条件之一成立时进入系统：

- 上传时使用的是没有当前前端限制的旧版本；
- 上传时部署环境的后端解压上限更高；
- 通过其他导入或生成路径写入；
- 当前源码与当时实际运行版本不一致。

无论历史原因属于哪一种，当前系统都出现了“系统允许继续使用历史包，但管理员无法把下载的原包重新上传”的不一致状态。

### 4.3 去重顺序不合理

后端 `TestcasePackageService.init()` 已经支持按 `(problemId, sha256)` 查找现有包。若相同 SHA 的包已经是 `READY`，后端可以直接返回现有包，无需再次上传分片。

但当前前端执行顺序是：

```text
选择文件
  -> JSZip 扫描并执行 50 MiB 解压总量限制
  -> 必要时生成 manifest.json
  -> 计算 SHA-256
  -> 调用 /init
  -> 上传分片
  -> 调用 /complete
```

由于深度 ZIP 扫描发生在 SHA 去重之前，历史大包会先被前端拒绝，后端已有的去重能力没有机会生效。

### 4.4 前后端限制可能漂移

后端限制可以通过环境变量修改，前端却使用编译期硬编码常量。如果运维只提高后端限制，前端仍会按 50 MiB 拒绝；如果只修改前端，后端会在 `/init` 或 `/complete` 阶段拒绝。

这会导致同一部署中的页面提示、接口行为和运维配置不一致。

### 4.5 错误信息缺少阶段和限制值

当前界面可能只呈现“操作失败”或统一兜底信息，没有稳定展示：

- 失败阶段是本地扫描、哈希计算、初始化、分片上传还是服务端校验；
- 实际压缩大小和解压总大小；
- 被哪个限制拒绝；
- 当前有效限制来自前端常量还是服务器配置；
- 可用于日志定位的 `traceId`。

这使普通的容量校验问题看起来像网络或服务器故障。

## 5. 处置原则

### 5.1 立即处置

在修复完成前：

1. 不要删除、归档或替换当前已激活的 `READY` 包。
2. 保存原始 ZIP、题目 ID、包 ID、文件大小和 SHA-256，至少保留一份独立备份。
3. 不要通过重新压缩、拆包后随意合并等方式直接覆盖生产包，避免 SHA、清单路径或测试数据发生变化。
4. 如必须迁移，应先在测试环境验证新包，再切换激活版本。

### 5.2 安全原则

不能简单取消解压总量限制。ZIP 炸弹、超高压缩比、超多条目和异常大单文件都可能耗尽服务器磁盘、CPU 或内存。

正式方案必须继续保留：

- 压缩文件大小限制；
- 解压总量限制；
- 单文件大小限制；
- ZIP 条目数限制；
- 路径穿越、重复条目和符号链接检查；
- 服务端权威校验；
- 临时文件清理和磁盘余量检查。

## 6. 修复方案

### 6.1 P0：保护现有数据并改善错误展示

前端应分别显示以下信息：

```text
ZIP 压缩大小：43.97 MiB / 允许 50 MiB
ZIP 解压总量：至少 99.00 MiB / 允许 50 MiB
失败阶段：浏览器本地扫描
失败原因：解压后总大小超过限制
```

本地异常不得统一转换为“操作失败”。对于 API 错误，应同时显示后端返回的业务错误、`errorKey`、可理解的参数和 `traceId`。

上传进度应明确区分：

- 扫描 ZIP；
- 生成清单；
- 计算 SHA-256；
- 初始化上传；
- 上传第 N/M 个分片；
- 服务端合并与校验；
- 完成或失败。

### 6.2 P1：统一容量配置

不要继续让前端独立硬编码服务器限制。建议由 problem-service 提供只读的测试包上传策略接口，例如：

```http
GET /api/v1/problems/testcase-package-policy
```

返回值至少包含：

```json
{
  "maxPackageBytes": 67108864,
  "chunkSizeBytes": 4194304,
  "maxCaseFileBytes": 8388608,
  "maxUncompressedBytes": 268435456,
  "maxEntryCount": 2000,
  "maxManifestBytes": 1048576
}
```

上述 `64 MiB / 256 MiB` 是覆盖当前案例的建议初始值，不应未经压测直接视为最终生产值。最终值应根据生产服务器磁盘、并发量、验证耗时和判题节点资源确定。

前端从该接口读取并显示限制；接口不可用时，可以使用保守默认值，但必须明确提示当前使用的是默认策略。后端环境变量仍然是最终权威值。

建议将不同限制拆分为不同常量和字段，禁止继续复用 `MAX_PACKAGE_BYTES` 表示解压总量。

### 6.3 P1：在深度扫描前完成历史包去重

增加只读的同题目 SHA 查询能力，例如：

```http
POST /api/v1/problems/{problemId}/testcase-packages/lookup
Content-Type: application/json

{
  "sha256": "...",
  "fileSizeBytes": 46109715
}
```

推荐流程：

```text
选择 ZIP
  -> 校验扩展名和压缩文件大小
  -> 计算原始 ZIP 的 SHA-256
  -> 查询同题目、同 SHA 的现有包
      -> 已存在 READY：直接返回并提示“测试包已存在，无需重复上传”
      -> 不存在：继续本地 ZIP 扫描
  -> 必要时生成 manifest.json，并重新计算最终 ZIP 的 SHA-256
  -> 调用 /init
  -> 分片上传
  -> /complete 服务端权威校验
```

这里建议使用独立的只读查询接口，而不是直接提前调用现有 `/init`。原因是缺少 `manifest.json` 的 ZIP 还会被前端重新生成，最终上传文件的 SHA 与原始文件不同；提前创建上传会话会产生无效会话和临时状态。

查重必须限定在用户有权管理的题目内，不能通过 SHA 查询泄露其他题目的包信息。

### 6.4 P1：提高解压上限但保留防护

对于确实需要大型数据的题目，可将解压总量上限提高到经过压测的值。建议初始评估：

| 项目 | 当前默认值 | 建议评估值 |
| --- | ---: | ---: |
| ZIP 压缩文件 | 50 MiB | 64 MiB |
| 解压后总量 | 50 MiB | 256 MiB |
| 单文件 | 8 MiB | 暂时保持 8 MiB |
| ZIP 条目数 | 2000 | 暂时保持 2000 |
| 上传分片 | 4 MiB | 暂时保持 4 MiB |

同时建议增加：

- 压缩比上限及异常压缩比告警；
- 上传前的可用磁盘空间检查；
- 单用户和单题目的并发上传限制；
- 临时目录配额及过期会话清理；
- `/complete` 阶段的任务超时和耗时指标；
- 上传、合并、校验阶段的审计日志。

### 6.5 P2：改善大文件上传可靠性

当前 4 MiB 顺序分片机制可以继续使用，但应增加：

1. 单分片有限次数重试，采用指数退避。
2. 页面刷新或网络中断后，根据上传会话状态恢复未完成分片。
3. 明确区分可重试错误与格式校验错误。
4. 哈希和 ZIP 扫描移入 Web Worker，避免大包处理期间阻塞管理页面。
5. `/complete` 如可能超过网关响应超时，应改为快速返回 `PROCESSING`，由持久化后台任务完成合并和校验，前端轮询状态。
6. 合并、校验失败后保存可读错误，同时可靠清理临时分片。

### 6.6 P2：改善大文件下载

当前前端以 `response.blob()` 接收完整响应后才触发保存。大包下载时，用户会长时间看不到浏览器保存进度，也不具备断点续传能力。

建议：

- 下载接口支持标准 `Content-Length`、`Content-Disposition`、`ETag` 和 `Range`；
- 大文件使用浏览器原生下载或可流式写入的下载方式；
- 支持断点续传和失败重试；
- 下载完成后可选择校验 SHA-256；
- 页面显示准备下载、传输中和校验中的不同状态。

## 7. 不建议采用的方案

以下做法不能作为正式修复：

1. 直接删除所有大小限制。
2. 只修改前端的 50 MiB 常量。
3. 只修改后端环境变量而不向前端暴露实际策略。
4. 为了重新上传而删除当前唯一的激活包。
5. 依赖浏览器校验替代服务端校验。
6. 把所有错误继续显示为“操作失败”。
7. 未经资源评估直接允许数 GiB 的 ZIP 或无限解压。

## 8. 验收标准

### 8.1 当前案例

使用同一题目下、SHA-256 为 `91d428...982` 的原始 `88.zip`：

- 系统在计算 SHA 后识别已有 `READY` 包；
- 不上传任何分片；
- 不重新执行服务端解压校验；
- 页面提示测试包已经存在；
- 原有激活状态和数据不受影响。

### 8.2 新大型测试包

使用压缩大小约 44 MiB、解压总量大于 50 MiB但小于部署策略上限的新包：

- 前端可以完成扫描、哈希和分片上传；
- 后端可以完成合并及权威校验；
- 页面显示真实阶段和进度；
- 最终包状态为 `READY`，用例数及各文件大小正确。

### 8.3 边界与安全测试

必须覆盖：

- 压缩文件恰好等于和超过上限；
- 解压总量恰好等于和超过上限；
- 单文件恰好等于和超过上限；
- 条目数恰好等于和超过上限；
- 高压缩比 ZIP；
- 路径穿越、重复路径、符号链接和损坏 ZIP；
- 缺少或损坏的 `manifest.json`；
- 上传中断、分片重复、分片 SHA 不一致和断点恢复；
- 前端策略获取失败；
- 部署环境变量变更后前端展示与后端行为一致；
- `/complete` 长时间处理时不被网关错误地判定为上传失败。

## 9. 实施顺序

1. 备份并保护现有 `88.zip` 及数据库记录。
2. 修复错误展示，确保能够区分本地扫描失败和 API 失败。
3. 增加服务器上传策略接口，移除前端限制硬编码和语义复用。
4. 增加授权范围内的 SHA 查重接口，并把历史包查重放到深度扫描之前。
5. 在测试环境评估并提高解压总量上限。
6. 补充后端验证、前端流程和历史大包兼容测试。
7. 根据压测结果上线分片重试、后台校验、下载 Range 和监控指标。

## 10. 结论

本次失败不是 44 MB 的 ZIP 超过压缩文件限制，也不是 88 个测试点过多，而是 ZIP 解压后的总大小超过前端硬编码的 50 MiB 限制。由于失败发生在浏览器本地扫描阶段，上传接口没有收到请求。

问题的正式修复不能只提高一个数值。需要同时解决历史包兼容、前后端配置统一、SHA 去重顺序、服务端安全校验、错误可观测性以及大文件传输可靠性，才能形成可以长期使用的测试数据管理能力。
