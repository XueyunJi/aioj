# 2026-08-28 AI 出题模块恢复生产修复记录

## 目标

本次工作聚焦独立的 AI 出题模块，不依赖学生端 AI 辅助输出。首日恢复生产主要解决以下问题：

1. 官方隐藏测试点生成后未被全量验证、全量打包的问题。
2. 错误引入的“AI API 调用超过 5 轮后停止出题”限制。
3. 教师通过改写建议重新生成题目时，模型返回无效 JSON，系统直接放弃改写的问题。
4. 建立本地多次修改和验证、最终才构建发布镜像的开发方式。

## 修复内容

### 1. 隐藏测试点全量覆盖

适用于所有题目难度，统一执行以下强约束：

- 生成器实际生成多少个测试输入，验证阶段就必须执行多少个。
- 官方包必须包含同样数量的 `.in` 和 `.out` 文件。
- 生成数、验证数、打包数任意不一致时，验证失败。
- 任意一个测试点未通过时，整体验证失败，不能生成通过状态的官方包。
- 不再使用抽样执行隐藏测试点来代替全量验证。

验收报告应满足：

```text
generatedInputCount == generatedOutputCount == caseCount == 实际执行用例数
```

且每一个测试用例状态均为 `ACCEPTED`。

### 2. 回退全局 5 轮 AI API 限制

此前增加的“累计 AI 调用达到 5 轮后停止生成”属于错误设计，已从业务流程移除：

- 不再通过全局轮次预算阻断题目生成或重新生成。
- 不再维护或消费题目草稿的 AI 调用轮次。
- 保留已执行过的 Flyway 迁移文件，避免已有数据库出现迁移校验冲突，但业务不再读取该字段。
- 单个流程已有的、针对具体自动修复步骤的重试策略不受影响。

### 3. 重新生成草稿的 JSON 恢复机制

原流程在 `regenerateProblemDraft` 返回非法 JSON 时直接返回 `INVALID`，而首次生成流程具备一次 JSON 修复机会，两条路径行为不一致。

现流程调整为：

1. 解析重新生成的完整题目草稿。
2. 若 JSON 解析或 Schema 校验失败，将原始响应和具体错误交给模型修复一次。
3. 对修复后的响应再次执行完整解析和 Schema 校验。
4. 只有修复后仍不合法，才保留原题并返回失败，不覆盖已有有效草稿。

针对完整草稿包含题面、标程、样例和测试生成器、内容较长的特点，同时完成以下调整：

- 完整草稿最大输出预算由 `6,400` 提升为 `16,000 tokens`。
- JSON 修复提示中保留的原始响应由最多 `12,000` 字符提升为 `50,000` 字符。
- 增加安全诊断日志，记录草稿 ID、响应长度、completion token 数和异常摘要。
- 日志不记录 API Key、数据库密码或完整题目响应。

主要实现文件：

```text
backend/ai-service/src/main/java/com/aioj/next/ai/domain/OpenAiCompatibleProvider.java
```

### 4. 本地开发运行方式

新增本地开发依赖编排和启动脚本：

```text
deploy/compose.dev.yml
scripts/dev-start.ps1
```

日常开发方式：

1. Docker 只运行 MySQL、Redis、RabbitMQ、Sandbox 等依赖。
2. Java 服务通过 IDE 或 Maven 在本机运行。
3. 多次修改、编译和本地验证不重建业务镜像。
4. 功能验收完成后，再统一构建镜像并推送发布。

## 功能验收清单

- [ ] 使用教师“改写建议”重新生成题目，能够得到合法完整草稿。
- [ ] 首次模型响应非法时，系统执行一次 JSON 修复并重新校验。
- [ ] 修复仍失败时，原有效题目保持不变，并可通过日志看到具体失败原因。
- [ ] 不因累计 AI API 调用超过 5 次而终止题目生成。
- [ ] 所有难度的题目均执行全部已生成隐藏测试点。
- [ ] 验证报告中的生成数、输出数、打包数和执行数完全一致。
- [ ] 任意隐藏测试点失败时，官方包验证不能标记为通过。
