## 一、已确认的问题

### P0：编译阶段状态被错误归类

`SandboxExecutionClient.compileSource()` 收到沙箱非 `Accepted` 结果时，只返回 `CompileOutcome.failed`，丢失沙箱原始 `status`。`SandboxClient.judge()` 随后把所有编译失败统一写成 `COMPILE_ERROR`。

实际后果：编译阶段的内存超限、超时、信号终止和沙箱错误都会显示为“编译错误”。

### P1：自定义校验器异常被错误归类

`runChecker()` 将 checker 的所有非 `Accepted` 状态统一转换为 `SYSTEM_ERROR`，导致 checker 超时、内存超限和运行错误无法准确反馈。

### P1：信号错误信息不完整

运行结果为 `Signalled` 时系统只显示“运行错误 / Signalled”。退出信号虽然写入审计日志，但没有体现在学生可见的判题消息中。应至少显示 signal 编号，常见信号应显示名称，例如 `SIGSEGV (signal 11)`。

### P2：编译资源策略不合理

编译内存当前为 `题目内存限制 × 2`。低内存题目可能导致 g++/javac 在编译阶段被沙箱杀死；提高题目运行内存会同时改变学生程序的正式运行约束。还需核查 sandbox 容器自身是否存在 128 MB 等硬上限。

## 二、修复目标

### 编译阶段与运行阶段的区分原则

两者不是靠内存数值区分，而是靠判题流程阶段区分：

```text
提交
  -> compileSource（仅对 C/C++/Java）
       -> 沙箱 status=Memory Limit Exceeded
          -> 编译阶段 MLE
  -> runCase（使用已生成的可执行文件/字节码）
       -> 沙箱 status=Memory Limit Exceeded
          -> 运行阶段 MLE
```

判定规则：

1. `compileSource()` 调用的沙箱命令是编译器（如 `g++`、`javac`），其返回的 `Memory Limit Exceeded` 只能标记为“编译阶段内存超限”。
2. 编译成功并获得 `fileId` 后，`runCase()` 调用学生程序；此阶段返回的 `Memory Limit Exceeded` 才是“运行阶段内存超限”。
3. Python 没有独立编译阶段，所有 MLE 都属于运行阶段。
4. 不能依据 `memoryKb` 是否接近限制来判断阶段。该字段只能作为证据，阶段由调用位置确定。
5. 数据库当前只有统一的 `status` 字段，建议在 `judge_audit_logs` 中增加 `phase`（`compile`、`run`、`checker`），学生可见消息可使用“编译阶段内存超限”和“运行阶段内存超限”两种明确文案。

编译阶段的状态转换必须保留原始沙箱状态；不能因为结果对象名为 `CompileOutcome`，就把所有失败都转换成 `COMPILE_ERROR`。

### 用户端区分方式

当前 `SubmissionStatus` 中只有一个 `MEMORY_LIMIT_EXCEEDED`，仅凭 status 无法区分两个阶段。不要新增两个互不兼容的状态枚举，采用“统一状态 + 判题阶段”的兼容方案：

```json
{
  "status": "MEMORY_LIMIT_EXCEEDED",
  "phase": "compile",
  "message": "编译阶段内存超限"
}
```

运行阶段示例：

```json
{
  "status": "MEMORY_LIMIT_EXCEEDED",
  "phase": "run",
  "message": "运行阶段内存超限"
}
```

实现要求：

1. 判题结果对象增加 `phase`：`compile`、`run`、`checker`。
2. `submissions` 增加 `judge_phase` 字段；历史记录为空时按旧 `status` 兼容展示。
3. API 返回 `status`、`phase` 和用户可读 `message`，前端禁止只根据 status 猜测阶段。
4. 编译阶段 MLE 的提示应说明这是编译器资源问题，通常不是学生算法错误；运行阶段 MLE 则提示检查程序的数据结构、数组、递归和内存占用。
5. `submission_case_results` 和 `judge_audit_logs` 同步记录 phase，确保详情页、管理端和审计记录一致。

保证沙箱原始终态在判题服务中不丢失，并在数据库、API 和前端保持一致：

| 场景 | 最终状态 |
|---|---|
| 编译器语法/链接错误 | `COMPILE_ERROR` |
| 编译阶段超时 | `TIME_LIMIT_EXCEEDED` |
| 编译阶段内存超限 | `MEMORY_LIMIT_EXCEEDED` |
| 编译阶段信号终止 | `RUNTIME_ERROR` |
| 学生程序超时 | `TIME_LIMIT_EXCEEDED` |
| 学生程序内存超限 | `MEMORY_LIMIT_EXCEEDED` |
| 学生程序信号终止 | `RUNTIME_ERROR` |
| checker 超时/内存超限/信号终止 | 保留对应状态 |
| 沙箱不可用、响应为空或协议错误 | `SYSTEM_ERROR` |

## 三、实施计划

### 阶段 1：统一沙箱结果模型

1. 扩展 `CompileOutcome`，保存原始沙箱 `status`、`error`、`fileError`、退出码、时间和内存。
2. 在 `SandboxExecutionClient` 增加统一的沙箱状态转换方法，至少覆盖 `Accepted`、`Time Limit Exceeded`、`Memory Limit Exceeded`、`Output Limit Exceeded`、`Nonzero Exit Status`、`Signalled`、`File Error`、`Internal Error`。
3. 编译阶段只把真正的编译失败映射为 `COMPILE_ERROR`；资源限制和信号状态按统一规则返回。
4. 保留编译器 stderr；对沙箱没有 stderr 的情况使用原始状态作为消息。

### 阶段 2：修复正式判题和 checker 映射

1. `SandboxClient.judge()` 使用编译结果的真实状态，而不是无条件使用 `COMPILE_ERROR`。
2. `runChecker()` 对 checker 沙箱结果直接保留映射后的状态；只有 checker 返回非法 JSON、未知业务状态或协议异常时才返回 `SYSTEM_ERROR`。
3. IOI 模式下生成的每个 case 结果使用同一个真实终态，汇总状态、得分和消息保持一致。
4. 明确区分学生程序的资源限制与 checker 自身的资源限制，避免把 checker 的资源错误伪装成学生程序错误。

### 阶段 3：改进错误消息和审计

1. 增加信号格式化方法：`11 -> SIGSEGV`、`6 -> SIGABRT`、`9 -> SIGKILL`、`8 -> SIGFPE` 等，未知信号显示 `signal N`。
2. 学生可见消息保留简洁原因，例如“运行错误：SIGSEGV (signal 11)”；完整 stderr 仍按现有长度限制保存。
3. 审计日志增加阶段字段（`compile`、`run`、`checker`）和沙箱原始状态，便于定位状态转换问题。
4. 对状态转换异常记录 submission ID、problem ID、sandbox status、exit status、memory 和 run time。

### 阶段 4：编译资源策略

1. 先确认 sandbox 是否存在容器级内存上限，以及请求中的 `memoryLimit` 是否被实际采用。
2. 将编译内存改为独立策略：
   - C/C++：`max(题目限制 × 2, 256 MB)`；
   - Java：`max(题目限制 × 2, 512 MB)`；
   - 编译 CPU 限制继续使用题目限制的放大值，但设置明确上限。
3. 学生程序运行阶段继续使用题目原始 `memory_limit_kb`，不因编译需要而改变题目语义。
4. 配置项化最低编译内存和编译倍数，默认值写入配置示例和部署文档。

## 四、测试计划

### 单元测试

- 编译成功：返回 `Accepted` 和 executable fileId。
- 编译语法错误：返回 `COMPILE_ERROR`，保留 stderr。
- 编译阶段 MLE：返回 `MEMORY_LIMIT_EXCEEDED`。
- 编译阶段 TLE：返回 `TIME_LIMIT_EXCEEDED`。
- 编译阶段 `Signalled`：返回 `RUNTIME_ERROR`，消息含 signal。
- 正式运行阶段的 WA、TLE、MLE、OLE、RE 均保持原有映射。
- checker 的 TLE、MLE、RE 不再变成 `SYSTEM_ERROR`。
- 沙箱空响应、HTTP 超时、协议错误仍返回 `SYSTEM_ERROR`。
- IOI 模式下 case 状态与汇总状态一致。

### 集成验收

使用真实沙箱分别提交：

1. 编译错误的 C++/Java 代码；
2. 编译阶段占用大量资源的代码；
3. 运行超时、运行内存超限、段错误和输出超限的代码；
4. 使用自定义 checker 且 checker 资源超限的题目。

核对数据库 `submissions`、`submission_case_results`、`judge_audit_logs`，确认状态、消息、时间、内存、退出码和 stderr 一致；再核对用户端显示文字。
