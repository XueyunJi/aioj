# 测试用例大规模上传出现的问题以及解决方案

## 1. 文档目的

本文记录 AIOJ 在上传大规模测试用例 ZIP 包时出现的兼容性、容量限制、性能和错误提示问题，并给出与当前源码一致的修复方案。

本文讨论的“包大小”必须区分以下概念：

1. ZIP 压缩文件大小。
2. ZIP 解压后的全部文件总大小。
3. 单个测试点文件大小。
4. ZIP 内文件条目数量。

不能使用同一个含糊的“50 MB 限制”描述上述四项，否则管理员无法判断失败发生在哪个环节。

## 2. 已复现问题

### 2.1 复现对象

现有题目中存在一个已经上传并激活的测试包：

| 字段 | 值 |
| --- | --- |
| 文件名 | `88.zip` |
| 压缩文件大小 | `46,109,715` 字节，约 `43.97 MiB` |
| SHA-256 | `91d4280b1732596bc85f7dbbe11b827a03de90cfef1fec8822943600498dc982` |
| 测试点数量 | 88 |
| 状态 | `READY` |
| 是否激活 | 是 |
| 存储方式 | `LOCAL` |

该包可以从系统下载，但下载后重新选择同一 ZIP 上传时，页面显示操作失败，浏览器 Network 面板没有出现 `/init`、分片上传或 `/complete` 请求。

### 2.2 关键证据

该 ZIP 的压缩文件大小没有超过当前前端的 50 MiB 限制，88 个测试点也没有超过 2000 个 ZIP 条目的限制，已记录的单个 `.in` 或 `.out` 文件均没有超过 8 MiB。

但是，仅第 71 至第 88 组测试点的输入、输出文件合计就达到：

```text
103,808,121 字节，约 99.00 MiB
```

因此，不需要计算全部 88 组文件，就可以确定该 ZIP 解压后的总大小必然超过 50 MiB。

## 3. 当前源码中的限制

### 3.1 前端限制

文件：`apps/web-admin-react/src/components/TestcasePackagePanel.tsx`

当前前端使用硬编码常量：

```ts
const CHUNK_SIZE_BYTES = 4 * 1024 * 1024;
const MAX_CASE_FILE_BYTES = 8 * 1024 * 1024;
const MAX_PACKAGE_BYTES = 50 * 1024 * 1024;
const MAX_MANIFEST_BYTES = 1 * 1024 * 1024;
```

其中 `MAX_PACKAGE_BYTES` 同时被用于：

- 检查 ZIP 压缩文件大小；
- 检查 ZIP 解压后的文件总大小；
- 检查前端补入 `manifest.json` 后重新生成的 ZIP 大小。

用户选择文件后，`prepareSelectedFile()` 会在浏览器中调用 `analyzeZip()`。`analyzeZip()` 使用 JSZip 读取 ZIP 中每个条目的 `uncompressedSize`，累计值超过 50 MiB 后立即抛出异常。

这个过程发生在计算完整 SHA-256 和调用上传初始化接口之前。因此，在该阶段失败时，Network 面板看不到上传请求是符合当前代码逻辑的。

### 3.2 后端限制

文件：

- `backend/problem-service/src/main/resources/application.yml`
- `backend/problem-service/src/main/java/com/aioj/next/problem/config/TestcaseProperties.java`
- `backend/problem-service/src/main/java/com/aioj/next/problem/domain/testcase/TestcasePackageValidator.java`

当前默认配置如下：

| 限制项 | 默认值 | 环境变量 |
| --- | ---: | --- |
| ZIP 压缩文件 | 50 MiB | `AIOJ_TESTCASE_MAX_PACKAGE_BYTES` |
| 上传分片 | 4 MiB | `AIOJ_TESTCASE_CHUNK_SIZE_BYTES` |
| 单个用例文件 | 8 MiB | `AIOJ_TESTCASE_MAX_CASE_FILE_BYTES` |
| 解压后总大小 | 50 MiB | `AIOJ_TESTCASE_MAX_UNCOMPRESSED_BYTES` |
| ZIP 条目数 | 2000 | `AIOJ_TESTCASE_MAX_ENTRY_COUNT` |
| `manifest.json` | 1 MiB | 当前为后端常量 |

后端在 `/complete` 阶段合并分片后，使用 `TestcasePackageValidator` 逐条读取 ZIP 内容，并再次执行单文件大小、解压总大小、条目数、清单格式和路径安全校验。后端校验必须保留，它是不能被浏览器绕过的权威校验。

## 4. 根因分析

### 4.1 直接根因：解压总量超过前端固定上限

`88.zip` 压缩后约 43.97 MiB，但解压后的总量远超 50 MiB。前端在本地扫描阶段拒绝文件，因此没有上传网络请求。

### 4.2 历史数据兼容性缺陷

服务器数据库中的该包已经是 `READY` 且处于激活状态，说明它可能在以下条件之一成立时进入系统：

- 上传时使用的是没有当前前端限制的旧版本；
- 上传时部署环境的后端解压上限更高；
- 通过其他导入或生成路径写入；
- 当前源码与当时实际运行版本不一致。

无论历史原因属于哪一种，当前系统都出现了“系统允许继续使用历史包，但管理员无法把下载的原包重新上传”的不一致状态。

### 4.3 去重顺序不合理

后端 `TestcasePackageService.init()` 已经支持按 `(problemId, sha256)` 查找现有包。若相同 SHA 的包已经是 `READY`，后端可以直接返回现有包，无需再次上传分片。

但当前前端执行顺序是：

```text
选择文件
  -> JSZip 扫描并执行 50 MiB 解压总量限制
  -> 必要时生成 manifest.json
  -> 计算 SHA-256
  -> 调用 /init
  -> 上传分片
  -> 调用 /complete
```

由于深度 ZIP 扫描发生在 SHA 去重之前，历史大包会先被前端拒绝，后端已有的去重能力没有机会生效。

### 4.4 前后端限制可能漂移

后端限制可以通过环境变量修改，前端却使用编译期硬编码常量。如果运维只提高后端限制，前端仍会按 50 MiB 拒绝；如果只修改前端，后端会在 `/init` 或 `/complete` 阶段拒绝。

这会导致同一部署中的页面提示、接口行为和运维配置不一致。

### 4.5 错误信息缺少阶段和限制值

当前界面可能只呈现“操作失败”或统一兜底信息，没有稳定展示：

- 失败阶段是本地扫描、哈希计算、初始化、分片上传还是服务端校验；
- 实际压缩大小和解压总大小；
- 被哪个限制拒绝；
- 当前有效限制来自前端常量还是服务器配置；
- 可用于日志定位的 `traceId`。

这使普通的容量校验问题看起来像网络或服务器故障。

## 5. 处置原则

### 5.1 立即处置

在修复完成前：

1. 不要删除、归档或替换当前已激活的 `READY` 包。
2. 保存原始 ZIP、题目 ID、包 ID、文件大小和 SHA-256，至少保留一份独立备份。
3. 不要通过重新压缩、拆包后随意合并等方式直接覆盖生产包，避免 SHA、清单路径或测试数据发生变化。
4. 如必须迁移，应先在测试环境验证新包，再切换激活版本。

### 5.2 安全原则

不能简单取消解压总量限制。ZIP 炸弹、超高压缩比、超多条目和异常大单文件都可能耗尽服务器磁盘、CPU 或内存。

正式方案必须继续保留：

- 压缩文件大小限制；
- 解压总量限制；
- 单文件大小限制；
- ZIP 条目数限制；
- 路径穿越、重复条目和符号链接检查；
- 服务端权威校验；
- 临时文件清理和磁盘余量检查。

## 6. 修复方案

### 6.1 P0：保护现有数据并改善错误展示

前端应分别显示以下信息：

```text
ZIP 压缩大小：43.97 MiB / 允许 50 MiB
ZIP 解压总量：至少 99.00 MiB / 允许 50 MiB
失败阶段：浏览器本地扫描
失败原因：解压后总大小超过限制
```

本地异常不得统一转换为“操作失败”。对于 API 错误，应同时显示后端返回的业务错误、`errorKey`、可理解的参数和 `traceId`。

上传进度应明确区分：

- 扫描 ZIP；
- 生成清单；
- 计算 SHA-256；
- 初始化上传；
- 上传第 N/M 个分片；
- 服务端合并与校验；
- 完成或失败。

### 6.2 P1：统一容量配置

不要继续让前端独立硬编码服务器限制。建议由 problem-service 提供只读的测试包上传策略接口，例如：

```http
GET /api/v1/problems/testcase-package-policy
```

返回值至少包含：

```json
{
  "maxPackageBytes": 67108864,
  "chunkSizeBytes": 4194304,
  "maxCaseFileBytes": 8388608,
  "maxUncompressedBytes": 268435456,
  "maxEntryCount": 2000,
  "maxManifestBytes": 1048576
}
```

上述 `64 MiB / 256 MiB` 是覆盖当前案例的建议初始值，不应未经压测直接视为最终生产值。最终值应根据生产服务器磁盘、并发量、验证耗时和判题节点资源确定。

前端从该接口读取并显示限制；接口不可用时，可以使用保守默认值，但必须明确提示当前使用的是默认策略。后端环境变量仍然是最终权威值。

建议将不同限制拆分为不同常量和字段，禁止继续复用 `MAX_PACKAGE_BYTES` 表示解压总量。

### 6.3 P1：在深度扫描前完成历史包去重

增加只读的同题目 SHA 查询能力，例如：

```http
POST /api/v1/problems/{problemId}/testcase-packages/lookup
Content-Type: application/json

{
  "sha256": "...",
  "fileSizeBytes": 46109715
}
```

推荐流程：

```text
选择 ZIP
  -> 校验扩展名和压缩文件大小
  -> 计算原始 ZIP 的 SHA-256
  -> 查询同题目、同 SHA 的现有包
      -> 已存在 READY：直接返回并提示“测试包已存在，无需重复上传”
      -> 不存在：继续本地 ZIP 扫描
  -> 必要时生成 manifest.json，并重新计算最终 ZIP 的 SHA-256
  -> 调用 /init
  -> 分片上传
  -> /complete 服务端权威校验
```

这里建议使用独立的只读查询接口，而不是直接提前调用现有 `/init`。原因是缺少 `manifest.json` 的 ZIP 还会被前端重新生成，最终上传文件的 SHA 与原始文件不同；提前创建上传会话会产生无效会话和临时状态。

查重必须限定在用户有权管理的题目内，不能通过 SHA 查询泄露其他题目的包信息。

### 6.4 P1：提高解压上限但保留防护

对于确实需要大型数据的题目，可将解压总量上限提高到经过压测的值。建议初始评估：

| 项目 | 当前默认值 | 建议评估值 |
| --- | ---: | ---: |
| ZIP 压缩文件 | 50 MiB | 64 MiB |
| 解压后总量 | 50 MiB | 256 MiB |
| 单文件 | 8 MiB | 暂时保持 8 MiB |
| ZIP 条目数 | 2000 | 暂时保持 2000 |
| 上传分片 | 4 MiB | 暂时保持 4 MiB |

同时建议增加：

- 压缩比上限及异常压缩比告警；
- 上传前的可用磁盘空间检查；
- 单用户和单题目的并发上传限制；
- 临时目录配额及过期会话清理；
- `/complete` 阶段的任务超时和耗时指标；
- 上传、合并、校验阶段的审计日志。

### 6.5 P2：改善大文件上传可靠性

当前 4 MiB 顺序分片机制可以继续使用，但应增加：

1. 单分片有限次数重试，采用指数退避。
2. 页面刷新或网络中断后，根据上传会话状态恢复未完成分片。
3. 明确区分可重试错误与格式校验错误。
4. 哈希和 ZIP 扫描移入 Web Worker，避免大包处理期间阻塞管理页面。
5. `/complete` 如可能超过网关响应超时，应改为快速返回 `PROCESSING`，由持久化后台任务完成合并和校验，前端轮询状态。
6. 合并、校验失败后保存可读错误，同时可靠清理临时分片。

### 6.6 P2：改善大文件下载

当前前端以 `response.blob()` 接收完整响应后才触发保存。大包下载时，用户会长时间看不到浏览器保存进度，也不具备断点续传能力。

建议：

- 下载接口支持标准 `Content-Length`、`Content-Disposition`、`ETag` 和 `Range`；
- 大文件使用浏览器原生下载或可流式写入的下载方式；
- 支持断点续传和失败重试；
- 下载完成后可选择校验 SHA-256；
- 页面显示准备下载、传输中和校验中的不同状态。

## 7. 不建议采用的方案

以下做法不能作为正式修复：

1. 直接删除所有大小限制。
2. 只修改前端的 50 MiB 常量。
3. 只修改后端环境变量而不向前端暴露实际策略。
4. 为了重新上传而删除当前唯一的激活包。
5. 依赖浏览器校验替代服务端校验。
6. 把所有错误继续显示为“操作失败”。
7. 未经资源评估直接允许数 GiB 的 ZIP 或无限解压。

## 8. 验收标准

### 8.1 当前案例

使用同一题目下、SHA-256 为 `91d428...982` 的原始 `88.zip`：

- 系统在计算 SHA 后识别已有 `READY` 包；
- 不上传任何分片；
- 不重新执行服务端解压校验；
- 页面提示测试包已经存在；
- 原有激活状态和数据不受影响。

### 8.2 新大型测试包

使用压缩大小约 44 MiB、解压总量大于 50 MiB但小于部署策略上限的新包：

- 前端可以完成扫描、哈希和分片上传；
- 后端可以完成合并及权威校验；
- 页面显示真实阶段和进度；
- 最终包状态为 `READY`，用例数及各文件大小正确。

### 8.3 边界与安全测试

必须覆盖：

- 压缩文件恰好等于和超过上限；
- 解压总量恰好等于和超过上限；
- 单文件恰好等于和超过上限；
- 条目数恰好等于和超过上限；
- 高压缩比 ZIP；
- 路径穿越、重复路径、符号链接和损坏 ZIP；
- 缺少或损坏的 `manifest.json`；
- 上传中断、分片重复、分片 SHA 不一致和断点恢复；
- 前端策略获取失败；
- 部署环境变量变更后前端展示与后端行为一致；
- `/complete` 长时间处理时不被网关错误地判定为上传失败。

## 9. 实施顺序

1. 备份并保护现有 `88.zip` 及数据库记录。
2. 修复 HTTPS Nginx 请求体和超时配置，确保正常的 4 MiB 分片能够通过代理。
3. 给分片请求增加服务端流式字节上限，防止异常请求占满磁盘。
4. 为上传完成流程增加状态抢占、事务边界和失败文件清理。
5. 修复错误展示，确保能够区分本地扫描失败和 API 失败。
6. 增加服务器上传策略接口，移除前端限制硬编码和语义复用。
7. 增加授权范围内的 SHA 查重接口，并把历史包查重放到深度扫描之前。
8. 增加过期会话、临时分片和判题缓存的定时清理。
9. 修复前端错误轮询结果和“失败即销毁会话”的行为，实现真正的断点续传。
10. 在测试环境评估并提高解压总量上限。
11. 补充后端验证、前端流程、并发竞争和历史大包兼容测试。
12. 根据压测结果上线后台校验、下载 Range、列表分页和监控指标。

## 10. 源码复审新增缺陷

以下问题来自对前端上传组件、API Client、problem-service、数据库迁移、Nginx、Gateway、judge-worker 和现有测试的进一步核对。严重程度表示在扩大测试包容量之前的处理优先级。

### 10.1 P0：分片请求体在落盘前没有字节上限

文件：

- `backend/problem-service/src/main/java/com/aioj/next/problem/controller/TestcasePackageController.java`
- `backend/problem-service/src/main/java/com/aioj/next/problem/domain/testcase/LocalTestcaseStorageService.java`
- `backend/problem-service/src/main/java/com/aioj/next/problem/domain/testcase/TestcasePackageService.java`

`uploadChunk()` 把 HTTP 输入流直接交给 `writeStagingChunk()`。存储层会一直读取到请求体结束并写入临时文件，然后业务层才调用 `validateChunkSize()` 判断实际大小是否等于期望分片大小。

这意味着攻击者或异常客户端可以把远大于 4 MiB 的请求体写入单个分片临时文件。即使最后返回“分片大小不匹配”，磁盘、网络和 I/O 已经被消耗，多个并发请求可以导致磁盘耗尽。

修复要求：

- 根据会话和分片序号先计算 `expectedChunkSize`；
- 存储层只允许读取 `expectedChunkSize + 1` 字节，超过时立即停止并删除临时文件；
- 同时在反向代理和应用服务器设置略高于合法分片的请求体上限；
- 对单用户、单题目和全局并发分片数限流。

### 10.2 P0：HTTPS Nginx 示例会拒绝合法分片

文件：`deploy/nginx/https-gateway.example.conf`

该 HTTPS 配置没有声明 `client_max_body_size`。Nginx 默认请求体上限通常为 1 MiB，而系统合法分片固定为 4 MiB，因此使用该示例部署时，合法分片可能在到达 Gateway 前直接返回 HTTP 413。

该配置也没有设置 `proxy_send_timeout` 和 `proxy_read_timeout`，通常会使用较短默认值，与 SPA 配置中的 900 秒以及 Gateway 的 240 秒不一致。

修复要求：

```nginx
client_max_body_size 8m;
proxy_connect_timeout 10s;
proxy_send_timeout 900s;
proxy_read_timeout 900s;
```

最终值应从合法分片大小推导，并在自动化部署检查中验证，不能依靠人工同步。

### 10.3 P0：`complete()` 缺少事务和并发状态抢占

文件：`backend/problem-service/src/main/java/com/aioj/next/problem/domain/testcase/TestcasePackageService.java`

上传完成流程会依次执行：

```text
会话改为 PROCESSING
  -> 合并文件并移动到最终 packages 目录
  -> 解压验证
  -> 删除旧用例和子任务
  -> 逐条插入新记录
  -> 包改为 READY
  -> 会话改为 READY
```

但是 `complete()` 没有事务注解，内部私有保存方法也没有有效的独立事务边界。数据库异常可能留下部分用例、包状态和会话状态不一致的结果。

同时，状态更新没有使用类似以下条件进行原子抢占：

```sql
UPDATE testcase_upload_sessions
SET status = 'PROCESSING'
WHERE id = ? AND status = 'UPLOADING';
```

两个并发 `/complete` 请求可能同时读取 `UPLOADING`，随后同时合并、验证、写库和删除临时目录。

修复要求：

- 使用条件更新或数据库锁保证只有一个请求取得处理权；
- 将数据库元数据落库放入明确事务；
- 文件系统操作采用“临时文件验证成功后再原子发布”的顺序；
- 数据库提交失败时清理未发布文件或记录补偿任务；
- 重复 `/complete` 必须幂等返回同一结果。

### 10.4 P0：无过期会话和临时文件清理任务

数据库保存了 `expires_at`，但当前只在客户端再次上传分片时检查过期。没有定时任务主动处理已经放弃的 `UPLOADING` 会话，也没有定期删除对应的：

- `tmp/{uploadId}` 分片目录；
- `testcase_upload_chunks` 记录；
- 旧上传会话记录；
- 合并中断产生的 `.merge-*` 文件。

因此，关闭页面、浏览器崩溃、断网或客户端不调用 `/fail` 都会造成长期磁盘和数据库垃圾。现有 `expires_at` 索引具备清理查询条件，但没有消费该索引的清理实现。

修复要求：增加持久化定时清理任务，采用小批量、可重入、带审计的方式，将过期上传标记为 `FAILED`，删除临时文件和分片记录，并清理超过保留期的历史会话。

### 10.5 P0：前端主动破坏断点续传

文件：`apps/web-admin-react/src/components/TestcasePackagePanel.tsx`

当前前端在 `/init` 成功后的任何异常中都会调用 `failUploadSession()`。一次短暂断网、单分片超时或浏览器请求失败，会立即把整个上传会话标为 `FAILED` 并删除已上传分片。

后端虽然提供上传状态和已上传分片索引，前端行为却使这些能力无法用于真正的断点续传。

修复要求：

- 网络错误和超时只暂停上传，不调用 `/fail`；
- 格式错误、用户明确取消或确认放弃时才终止会话；
- 保存 `problemId + fileSha256 + uploadId`，重新进入页面后查询状态；
- 对缺失分片继续上传，对已上传分片跳过；
- 终止操作需要用户明确确认。

### 10.6 P0：轮询超时会被错误标记为成功

`pollUntilReady()` 最多轮询 20 次，每次间隔 1.5 秒。若 30 秒内状态始终不是 `READY` 或 `FAILED`，函数会正常返回，调用方随后把页面阶段设置成 `ready`。

这会把仍处于 `PROCESSING`、停滞或状态接口异常的任务显示为上传成功。

修复要求：轮询达到截止时间后必须进入“仍在处理”或“查询超时”状态，绝不能进入 `READY`。应允许用户稍后继续查询，并以服务端状态为唯一成功依据。

### 10.7 P1：同步合并校验与 Gateway 超时冲突

problem-service 路由使用全局 `GATEWAY_RESPONSE_TIMEOUT=240s`，而 `/complete` 同步执行分片合并、整包 SHA-256、逐条解压和数据库写入。提高解压上限后，该请求更容易超过 240 秒。

客户端收到 504 时，服务端可能仍在处理，从而出现“前端认为失败、服务端稍后成功”的不确定结果。

正式方案应让 `/complete` 原子抢占状态后快速返回 `PROCESSING`，由持久化后台任务完成合并与验证。单纯把超时提高到 900 秒只能作为临时措施。

### 10.8 P1：失败 ZIP 会提前进入正式存储路径

`LocalTestcaseStorageService.mergePackage()` 在 ZIP 内容验证之前，就使用 `REPLACE_EXISTING` 把合并结果移动到：

```text
packages/{problemId}/{sha256}.zip
```

如果后续 ZIP 校验失败，该正式路径中的无效文件不会被清理。长期运行会产生失败包和孤儿文件，且正式目录不再只包含 `READY` 数据。

修复要求：合并到隔离的 staging 路径，完成大小、SHA 和 ZIP 验证后再原子发布；失败时删除 staging 文件。正式文件与数据库提交之间需要补偿或巡检机制。

### 10.9 P1：测试包列表接口返回过量数据并产生 N+1 查询

`list(problemId)` 查询包列表后，对每个包分别查询子任务和全部测试点。即一个题目有 N 个历史包时，会产生约 `1 + 2N` 次数据库查询，并把每个版本的全部 case 元数据返回给前端。

页面列表实际只显示版本、文件名、大小、状态和用例数量，但本次抓到的响应包含了 88 个完整 case 对象。历史版本和测试点继续增加后，会造成接口响应、JSON 解析和管理页面刷新变慢。

修复要求：

- 列表接口只返回包摘要；
- 包详情单独按需加载；
- case 列表分页或仅在编辑时获取；
- 避免逐包查询，使用批量查询或聚合结果。

### 10.10 P1：浏览器主线程内存和 CPU 放大

当前前端存在多重资源占用：

- `JSZip.loadAsync(file)` 在浏览器解析 ZIP；
- `blob.arrayBuffer()` 一次性把完整压缩包复制到内存计算 SHA-256；
- 每个分片再次 `arrayBuffer()` 并计算 SHA-256；
- 缺少 `manifest.json` 时，JSZip 会解压并重新压缩整个包；
- SHA-256 回退实现运行在主线程，大文件会冻结页面。

提高包上限后，上述问题会被同步放大，尤其在内存较小的电脑和浏览器中可能出现页面无响应或 OOM。

此外，前端通过 JSZip 私有字段 `_data.uncompressedSize` 获取解压大小。该字段不是稳定公共契约，依赖升级后可能变成 `undefined`，代码会将其当作 0，从而静默绕过前端总量检查。

修复要求：使用 Web Worker 和增量哈希；避免重复读取整包；不要依赖 JSZip 私有字段；对 ZIP 条目数在浏览器扫描早期设置上限；没有清单时评估由后端生成规范包，避免浏览器重压缩大型数据。

### 10.11 P1：本地存储不支持 problem-service 横向扩容

上传会话和分片元数据存储在数据库，但分片文件存储在 problem-service 本地卷。如果部署多个 problem-service 实例，而它们不共享同一个可靠文件系统，分片请求和 `/complete` 请求落到不同实例时会出现“数据库显示分片存在，但本机文件不存在”。

正式扩容前必须选择以下方案之一：

- 使用对象存储并支持分片上传；
- 使用所有实例可见的共享存储，并验证一致性和锁语义；
- 上传期间使用可靠的会话粘滞，但仍需处理实例故障迁移。

本地 Docker 单实例卷只能满足当前单节点部署，不能直接作为高可用方案。

### 10.12 P1：Judge Worker 缓存会持续增长并串行阻塞

文件：`backend/judge-worker/src/main/java/com/aioj/next/judge/domain/TestcasePackageCache.java`

每个 Judge Worker 会同时保留压缩 ZIP 和解压目录，但没有容量上限、LRU 淘汰、过期清理或磁盘水位保护。历史包版本越多，判题节点磁盘占用越大。以大型包为例，每个 Worker 可能同时占用约 44 MiB 压缩文件和超过 100 MiB 的解压数据。

`prepareActivePackage()` 使用方法级 `synchronized`，一个大型包的下载、SHA 校验和解压会阻塞该 Worker 上所有其他题目的测试包准备。内部下载客户端也没有显式连接和读取超时。

修复要求：按 `packageId/SHA` 使用细粒度锁；增加下载超时、临时文件和原子替换；实施缓存容量上限、LRU/TTL 淘汰、磁盘水位检查和指标告警。

### 10.13 P2：下载不支持断点续传

管理端下载接口返回 `InputStreamResource` 和 `Content-Length`，但没有实现 `Range`、`ETag` 和条件请求。前端 `requestBinary()` 使用 `response.blob()`，只有完整文件接收完毕后才触发保存。

大文件下载中断后只能从头开始，浏览器保存进度也无法直接反映后端传输过程。该问题与用户观察到的“44 MB 包下载十分慢”一致。

### 10.14 P2：会话创建者字段没有参与访问校验

上传会话记录了 `created_by`，但后续分片上传、状态查询、完成和失败操作只按 `problemId + uploadId` 查找会话，没有校验当前用户是否为会话创建者。

如果产品策略允许同一题目由多位教师协作，可以保留共同管理，但必须把它定义成显式权限；否则应限制为创建者或管理员，避免他人意外终止正在进行的上传。

### 10.15 P2：上传完成请求契约存在无效字段

`TestcaseUploadCompleteRequest` 定义了 `uploadedChunks` 和 `sha256`，但 `complete()` 没有使用这些字段，前端也只发送空对象 `{}`。这不是当前失败的直接原因，但会误导后续开发者认为服务端会校验请求中的完成信息。

应删除无效字段，或者明确实现并记录其幂等、校验语义。最终完整性仍应以数据库中的分片记录、服务端合并大小和服务端 SHA-256 为准。

### 10.16 P1：关键上传路径缺少测试

当前只有 `TestcasePackageServiceTest`，主要覆盖归档下载、失败状态和追加用例。没有发现以下专项测试：

- `/init` 新建、重复 SHA、过期会话和并发初始化；
- 分片精确大小、超长请求体、重复分片和并发分片；
- `/complete` 幂等、并发、数据库中途失败和文件补偿；
- `TestcasePackageValidator` 的总量、单文件、条目数、路径和损坏 ZIP 边界；
- `LocalTestcaseStorageService` 合并失败及临时文件清理；
- 前端 `analyzeZip()`、SHA、断点恢复和轮询超时；
- Nginx/Gateway 请求体与超时的部署级验证；
- Judge Worker 大包下载、解压、缓存淘汰和并发准备。

在调整容量限制前，应先建立这些测试，否则扩容会放大目前没有被自动化覆盖的资源和一致性风险。

## 11. 结论

本次失败不是 44 MB 的 ZIP 超过压缩文件限制，也不是 88 个测试点过多，而是 ZIP 解压后的总大小超过前端硬编码的 50 MiB 限制。由于失败发生在浏览器本地扫描阶段，上传接口没有收到请求。

问题的正式修复不能只提高一个数值。需要同时解决历史包兼容、前后端配置统一、SHA 去重顺序、服务端安全校验、错误可观测性以及大文件传输可靠性，才能形成可以长期使用的测试数据管理能力。
