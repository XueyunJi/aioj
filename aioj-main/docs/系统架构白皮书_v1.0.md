**版本：** v1.0

## 一、系统概述

AIOJ（AI-powered Online Judge）是面向校园教学场景的在线判题平台，核心定位是"AI 原生 OJ"。
原作者使用CODEX开发，当前作者会调用AI编程工具继续推进和完善。

系统覆盖教学全链路：
- **课前**：AI 辅助出题、题目草稿生成
- **课中**：学生在线练习、AI 答疑助教、比赛运行
- **课后**：异步判题、赛后 AI 复盘、学情画像

```
学生提交代码 → 网关鉴权 → 题目服务校验 → RabbitMQ 入队
  → judge-worker 消费 → go-judge 沙盒执行 → 结果回写 MySQL
  → WebSocket/SSE 推送前端
```

**AI 出题流：**
```
教师输入主题 → AI 服务生成 generationPlan → LLM 生成完整草稿
  → 静态校验 → 样例验证 → 隐藏点验证 → 对拍验证 → 复杂度分析
  → 全部通过 → 导入题库
  → 任一失败 → 根因分析 → AI 改写 → 重新验证
```

**AI 答疑流（Agent Core V3）：**
```
学生提问 → 建立 Turn → 构建 Bootstrap Context → LLM 生成回答/工具请求
  → 服务器逐次授权工具 → 执行合法工具 → 输出安全检查
  → 持久化审计证据 → 异步生成摘要
```

## 四、AI Agent 架构与原理

### 4.1 核心理念："模型是不可信规划器，服务器是可信控制面"

传统 AI 应用假设大模型是"助手"，系统直接执行模型的输出。
### 4.2 Agent Core V3 架构详解
Agent Core V3主要应用于AI辅助答疑功能。
#### 4.2.1 在线 Turn（对话轮次）

一次完整的 AI 交互被抽象为一个 **Turn**（轮次），具有稳定 ID 和终态：

```
用户请求
  → 服务端建立 Turn + 锁定身份/策略快照
  → 构建最小 Bootstrap Context
  → 模型提出回答或工具请求
  → 服务端逐次授权并执行工具
  → 汇总受信数据与模型输出
  → 输出安全检查
  → 持久化回答、用量、工具与审计证据
  → 异步生成可检索摘要
```

**关键设计：**
- **幂等重试**：Turn 有唯一 ID，网络抖动或 LLM 故障时可重试，避免重复计费、重复审计
- **终态管理**：每个 Turn 最终处于成功、失败、降级等确定状态
- **异步摘要**：回答后立即返回用户，摘要生成异步进行，不阻塞交互

#### 4.2.2 上下文分层（Context Hierarchy）

原始业务数据是权威源，摘要、向量、记忆都是派生数据。分五层：

| 层级 | 内容 | 控制权 | 作用 |
|------|------|--------|------|
| **Bootstrap Context** | 当前用户、会话、题目、比赛、能力边界的最小摘要 | 服务器生成 | 每轮对话的"开场白"，AI 只能接收 |
| **Turn 摘要** | 每轮结构化记录主题、实体引用、决定与未解决问题 | 服务器生成 | 短期记忆 |
| **Episode 摘要** | 跨多轮的阶段性上下文 | 服务器生成 | 中期记忆 |
| **原始证据回取** | 回答关键事实前回取受权原文或业务记录 | 服务器决定回取什么 | 防止 AI 胡说"题库里有这道题" |
| **精确检索兜底** | 摘要召回不足时使用受限关键字或实体检索 | 服务器执行 | 兜底机制 |

**关键设计：** AI 不拥有"记忆权"，它看到的上下文是服务器精心筛选后的**最小必要信息**，防止信息泄露和幻觉累积。

#### 4.2.3 工具控制面（Tool Control Plane）

模型只能看到当前场景允许的工具描述，每次调用都由服务器重新检查：

- **身份与角色**：当前用户是谁？学生/教师？
- **场景约束**：当前是否在比赛中？时间窗口？
- **参数 Schema**：工具参数是否符合预定义格式？
- **数据可见性**：最小返回字段，不暴露隐藏测试
- **预算与超时**：调用预算、超时时间、循环上限
- **审计与隐私**：是否符合隐私要求？

**关键设计：** 工具结果使用结构化数据并标注可信来源。网页、题面、用户内容、模型文本都不能作为系统指令改变工具权限——这是 Prompt Injection 防护的核心。

#### 4.2.4 记忆与学习画像（Memory & Learning Profile）

**长期记忆**：保存稳定、可复用且有证据的用户偏好或事实（如"我喜欢用 Python"、"我线段树薄弱"）。

**学习画像**：保存从提交、复盘和行为信号推导的能力状态。

**两者分离**，避免把一次题目知识点或 AI 建议误当作长期偏好。

**写入流程（Claim 机制）：**
```
证据 → 候选 → 质量/冲突检查 → 用户确认 → 生效 Claim
```

**关键设计：** 模型只能提出候选，不能直接写入。服务端保存证据、来源和状态；用户可以接受、拒绝或撤销；冲突 Claim 不静默覆盖。这防止了 AI 的"幻觉"直接污染用户档案。

#### 4.2.5 四层比赛安全（Contest Security）

这是 OJ 场景特有的纵深防御：

| 层级 | 机制 | 作用 |
|------|------|------|
| **参赛判定** | 服务器根据当前运行、参与者和时间窗口判断约束范围 | 确定学生是否处于比赛中 |
| **策略快照** | 将运行发布时固化的 AI 策略注入当前 Turn | 比赛中 AI 行为受预设策略约束（如禁止给完整代码） |
| **问题匹配** | 使用运行题目快照与受限指纹判断用户是否在询问比赛题 | 防止学生换说法套题 |
| **输出检查** | 返回前检查完整代码、私有题信息与其他受限内容 | 最后一道防线，拦截泄露 |

**关键设计：** 客户端传入的 `problemId` 或比赛上下文只用于体验和统计，不能作为可信授权依据。私有题面、隐藏测试和其他参与者源码不会发送给模型用于判断。

#### 4.2.6 Prompt Injection 防护

- **指令权隔离**：指令只来自可信服务器配置和受控策略，用户文本、历史消息、题面、工具结果都标记为"数据"
- **结构化工具返回**：工具返回结构化字段，不拼接成可执行系统指令
- **记忆写入确认**：记忆写入经过独立候选与确认流程
- **最终输出检查**：回答返回前执行内容与策略检查

### 4.3 AI 出题引擎原理

AI 出题模块不是 Agent Core V3 的一部分，而是独立的上层应用，但复用了部分底层能力（如沙盒调用、审计）。

#### 4.3.1 生成流程

```
教学主题输入
  → LLM 生成 generationPlan（核心算法、辅助算法、复杂度、边界）
  → LLM 生成完整题目草稿：
      - 题面（title, description, inputFormat, outputFormat, hint）
      - 样例（testCases: input + expectedOutput）
      - 标程（standardSolutionCode）
      - 参考解/暴力解（referenceSolutionCode）
      - 数据生成器（testcaseGeneratorPython）
      - 压力测试生成器（stressTestcaseGeneratorPython）
      - 复杂度声明（complexity）
  → 静态校验（字段完整性、格式、依赖检查）
  → 样例验证（标程跑样例，输出比对）
  → 隐藏点验证（生成器生成隐藏数据，标程跑）
  → 对拍验证（标程输出 vs 参考解输出）
  → 复杂度分析（静态分析标程，比对声明）
  → 全部通过 → 导入题库
  → 任一失败 → 根因分析 → AI 改写 → 重新验证
```

#### 4.3.2 验证引擎设计

验证引擎是 AI 出题的核心，但目前是**生成流程的子步骤**，而非独立服务。包含五个验证阶段：

| 阶段 | 检查内容 | 失败常见原因 |
|------|---------|-------------|
| **静态校验** | 字段完整、复杂度格式、stress generator 存在性 | 字段缺失、括号未闭合 |
| **样例验证** | 标程跑样例，输出等于 expectedOutput | 样例手算错误、标程 bug |
| **隐藏点验证** | 生成器生成数据，标程跑 | 边界数据不足、标程未处理极端情况 |
| **对拍验证** | 标程 vs 参考解，输出一致 | 标程逻辑错误、参考解错误 |
| **复杂度分析** | AST 静态分析，比对声明 | 误判标准 DP/线段树、声明格式错误 |

#### 4.3.3 AI 改写机制

验证失败后，系统进入改写循环：

```
验证报告 → 根因分析（Rule-based）→ 确定 suspectFields
  → 构建 Rewrite Prompt（含根因、允许修改字段、历史修改记录）
  → LLM 生成修改候选（JSON 格式）
  → 字段级权限检查（只允许修改 suspectFields 中的字段）
  → 用户确认（或自动确认）→ 生效
  → 触发重新验证
```

**关键设计：** 字段权限是动态的，根据根因决定。例如：
- 根因是"样例输出错误" → 允许修改 `testCases.expectedOutput`，但禁止修改 `testCases.input`（防止题意篡改）
- 根因是"标程逻辑错误" → 允许修改 `standardSolutionCode`
- 根因是"数据生成器不足" → 允许修改 `testcaseGeneratorPython`

## 五、AI Agent 的作用

### 5.1 对教师的作用

| 场景 | 传统 OJ | AIOJ |
|------|---------|------|

### 5.3 对平台的作用

|------|------|

| **数据资产** | 学习画像积累形成可分析的教学大数据 |
| **安全合规** | 受审计的 AI 交互满足教育场景的合规要求 |

## 六、创新性分析

### 6.1 架构层面创新

#### 6.1.1 "模型不可信"的安全架构

**业界现状：** 大多数 AI 应用将大模型视为"可信助手"，系统直接执行模型输出。

**AIOJ 创新：** 建立"模型是不可信规划器，服务器是可信控制面"的架构哲学。所有模型输出必须经过服务器授权、检查、审计后才能生效。这不是简单的"加一层过滤"，而是**从架构层面将 AI 降级为"建议者"，将控制权牢牢掌握在服务端**。

**价值：** 在教育场景（涉及成绩、比赛公平性、隐私）中，这种架构是**必要条件而非可选项**。

#### 6.1.2 四层比赛安全纵深防御

**业界现状：** 一般 OJ 的比赛防作弊依赖"封榜"、"代码查重"等事后手段。

**AIOJ 创新：** 将 AI 答疑纳入比赛安全体系，建立"参赛判定 → 策略快照 → 问题匹配 → 输出检查"的四层实时防护。即使在 AI 原生交互场景下，也能保证比赛公平性。

**价值：** 这是"AI 原生 OJ"区别于"传统 OJ + AI 插件"的关键标志。

#### 6.1.3 端到端 AI 出题与自验证闭环

**业界现状：** OJ 题目全靠人工或半自动工具生成，AI 最多辅助写题面。

**AIOJ 创新：** 让 AI 同时完成命题、写标程、写暴力解、写数据生成器、声明复杂度，并建立"生成-验证-根因分析-改写-再验证"的闭环。

**价值：** 将单题生产时间从数小时压缩到数十分钟，且通过多维度验证保证质量。

### 6.2 工程层面创新

#### 6.2.1 Turn 机制的幂等设计

AI 交互的幂等性设计（稳定 ID、终态管理、异步摘要）在对话系统中并不常见，但在**计费敏感、审计严格的教育场景**中是必要的。

#### 6.2.2 记忆与画像的分离 + Claim 确认机制

将"用户偏好"（记忆）和"能力状态"（画像）分离，并引入"候选-确认"机制，防止 AI 幻觉污染用户档案。这种设计在推荐系统中常见，但在教育 AI 中是一种**负责任的工程实践**。

#### 6.2.3 不可变部署与供应链安全

按 digest 部署、生成 SBOM/构建证明，这些在云原生领域是最佳实践，但在学生项目中实现，体现了**超越一般课设的工程成熟度**。

### 6.3 场景层面创新

#### 6.3.1 "AI 原生"而非"AI 附加"

不是给传统 OJ 加个 ChatBot，而是从架构层面让 AI 参与出题、答疑、复盘、画像的全链路。

#### 6.3.2 教学闭环

覆盖"课前（AI 出题）→ 课中（练习+答疑）→ 课后（复盘+画像）"的完整教学周期，而非孤立的判题工具。

## 七、已知局限与改进方向

### 7.1 已确认的工程缺陷（基于测试暴露）

| 模块 | 问题 | 影响 | 改进方向 |
|------|------|------|---------|
| **AI 出题** | 验证链路不完整（无独立服务、无状态机、无重验） | 隐藏点抽样验证、修复死锁 | 抽离为独立 Validation Domain Service |
| **AI 出题** | AI 服务层缺防御（无超时熔断、无 JSON 容错） | 700秒挂死、JSON解析崩溃 | 接入 Resilience4j、强制 JSON Mode |
| **AI 出题** | 沙盒调用层缺统一抽象 | CWD不稳定、路径混乱 | 建立 SandboxPathResolver |
| **AI 出题** | 复杂度分析器过于粗暴 | 误判标准DP/线段树 | 引入算法白名单配置 |
| **AI 出题** | 困难题"凭空创造" | 质量不稳定、标程不标准 | 引入 RAG + 真题 Few-shot |
| **安全架构** | 生产拓扑为单机合并（成本妥协） | 容器逃逸风险 | 恢复双节点或加 Docker 网络隔离 |
| **配置管理** | 本地秘密分散，不纳入版本控制 | 交接困难、配置丢失风险 | 集中化配置管理（Spring Cloud Config / Vault） |

### 7.2 架构层面的待完善

| 方向 | 说明 |
|------|------|
| **RAG 增强** | 困难题生成时引入向量检索（CCPC/ICPC 真题 Few-shot） |
| **多模态** | 支持图片题面、数学公式渲染、代码可视化 |
| **联邦学习** | 跨校学习画像联合建模（隐私保护前提下） |
| **AIOps** | AI 服务的可观测性（调用链追踪、成本分析、模型效果评估） |

## 八、总结

AIOJ 是一个**架构理念先进、工程实现有短板、场景定位清晰**的 AI 原生 OJ 项目。

其核心价值在于：
1. **建立了"模型不可信"的教育 AI 安全范式**，将 AI 能力内嵌为系统一级公民而非外挂
2. **覆盖了教学全链路**（出题-练习-答疑-复盘-画像），形成闭环
3. **在 OJ 场景中实现了端到端 AI 出题与自验证**，具有明确的效率提升价值

当前的主要任务是**将先进的架构理念工程化**——补齐验证引擎、AI 服务防御、沙盒治理等工程短板，使系统从"原型级"提升到"生产级"。
